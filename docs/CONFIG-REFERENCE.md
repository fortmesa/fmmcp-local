This is the single knob matrix for `~/.fmcode/config.json`. `README.md`
(CLI humans), `AGENTS.md`/`.agent/*` (LLM agents), and `docs/VSIX.md` (VSIX
humans) should link here instead of restating it (`VSIX-PLAN.md` §5, D-V9).

`config.json`'s canonical shape is defined and validated by the zod schema in
`src/registry/config.ts`; every field below is a property of that schema.
Precedence at proxy startup is **CLI startup flags > `config.json` >
built-in defaults** (`resolveEffectiveStartup`); once the proxy is running,
only `config.json` drives hot-reload (`watchConfig`) — startup flags are not
re-consulted.

**Decision enforced by this table (D-V8)**: every `config.json` knob is
exposed as a `fortmesa.*` VS Code setting, and — per the _inverse_ constraint
— no `fortmesa.*` setting may exist without a corresponding Saferoom UX
control. One knob (`environments`) still fails that inverse constraint; it is
marked **⚠️ D-V8 GAP** in the table and listed again in
[§ Known gaps](#known-gaps-as-built) below so it isn't missed. The `ideSync.*`
and `logLevel` gaps noted in earlier revisions of this file were resolved by
the R3/R8 revision slice (see `.agent/DECISIONS.md` D012) and are marked
resolved in the table below.

## Known gaps (as-built)

As of UX Round 2 (`.agent/planning/UX-ROUND-2-PLAN.md`), one `fortmesa.*`
setting still has **no working Saferoom UX control** to add or edit entries
(only to select among existing ones), i.e. one remaining violation of D-V8's
inverse constraint ("no setting may exist that the Saferoom UX cannot
configure"). This is reported here as a defect for the orchestrator to
schedule against the phase that owns it (D-V8 in `VSIX-PLAN.md` §9) — this
file does not paper over it by inventing a UI reference that doesn't exist
yet.

1. **`fortmesa.environments`** — the Environment picker (now in the
   "Settings" webview, W10) and the CLI's `switch --env` can only
   _select_ one of the environments already present in the map; nothing in
   the Saferoom UI (or the CLI) can add a new environment or change an
   existing one's `gateway` URL. The only paths today are hand-editing
   `config.json` or editing the `fortmesa.environments` JSON object in VS
   Code's Settings UI. Tracked in `TODOS.md` as the `environments` add/edit
   UX item; explicitly deferred, not forgotten. (Separately, the _values_
   `config.json` should default to for `sandbox`/`next`/`latest`/`prod` are
   now single-sourced in `src/registry/environments.ts`, W2 — that closes the
   two-place drift bug this file used to warn about, but doesn't add
   add/edit UX, which is a different gap.)

All other settings that had gap notes in earlier revisions of this file are
now marked **✅ Resolved** in the table above — `fortmesa.ideSync.*` (all five
targets, now controlled from the "Settings" webview's **Agents**
section), `fortmesa.ideSync.vscode` specifically (real effect on VS Code's
own MCP registration), and `fortmesa.logLevel` (real effect on the
extension's OutputChannel filtering).

The table's "Saferoom UI control" cell for the affected row above points
straight at this section instead of describing a control that doesn't exist.

## Adjacent, deliberately setting-less stores

Two things a reader might expect in the table above are **intentionally not
`config.json` keys** and therefore have no `fortmesa.*` setting — this is a
correct application of D-V4, not an oversight:

- **`credentials.json`** (`~/.fmcode/credentials.json`, per-environment
  `{ fortmesa_api_token, fortmesa_api_base, scopeMap }`) — the token store is
  never exposed as a VS Code setting because settings (`settings.json`) are
  plaintext and often synced/backed up; secrets never belong there (D-V4:
  `credentials.json`, mode `0600`, is the _only_ store). It's still fully
  CLI/UI-reachable, just through the **Auth** surface instead of a setting:
  - CLI: `fmmcp-local token set <env> <token> [--base <url>]`,
    `fmmcp-local login [--env <name>] [--no-browser]`.
  - Saferoom UI (all real, `src/extension/identity-view.ts` +
    `src/extension/auth-commands.ts` + `src/extension/login-command.ts`): the
    **Signed-in user** pane is a webview whose primary action is **Sign in**
    (`fortmesa.login` — the default route; the fmweb-be OAuth blockers,
    curriculum 03-token-and-oauth.md, aren't resolved yet). Pasting an
    access token is an inline **Advanced** disclosure in that same pane,
    carrying its own data-region `<select>` — that select is the only way to
    seed credentials for a NON-active environment. **Sign out** is a button
    in the pane and has **no confirmation at all** (PO, 2026-09-08 — the
    inline strip that replaced the modal was itself removed). One click
    clears the stored token and refresh token; nothing is revoked. For a
    pasted access token the button reads **Remove**, because the token stays
    valid wherever else it is used.
    Removed 2026-09-03: `fortmesa.mintToken` / `fmmcp-local token mint`
    (minting rotated an existing M2M token and could not bootstrap one, so
    it only lowered resistance to the discouraged path), plus the
    `fortmesa.pasteToken` and `fortmesa.signOut` palette commands, whose
    replacements are inline.
  - The API **base URL** (`fortmesa_api_base`, the host identity and every
    other REST call is sent to) lives in this file too, and is a different URL
    from `config.json`'s `environments.<env>.gateway` (the MCP transport
    endpoint) — don't conflate the two when reading either file. It does
    **not** decide the OAuth audience: for a built-in environment the RFC 8707
    `resource` indicator comes from `src/registry/environments.ts`'s `api`,
    the same single source of truth the `client_id` comes from
    (`src/registry/oauth-provider.ts`). A branded/vanity alias of the same
    servers (e.g. `https://api.vciso.app` for production) is not a registered
    Auth0 resource server, and sending it as the audience fails the sign-in
    outright with `access_denied : Service not found: <url>` — fixed
    2026-09-08.
- **`environments.<env>.scopeMap`** inside `credentials.json` (scope name →
  scope ID cache) — an implementation-detail cache populated automatically by
  `fmmcp-local scopes list`, the Scope selector panel, and the hot-reload scope-lock
  resolver; it is never hand-configured by a human via any surface, so a
  settings mirror would serve no purpose.
- **`src/registry/environments.ts`'s `app` URL** (per environment) — not a
  `config.json` field, not a `fortmesa.*` setting, and not user-editable
  through any surface. All four values (`sandbox`/`next`/`latest`/`prod`) are
  hardcoded (D-U7/D-U9, 2026-07-06: "not worth the complexity; no BrandAsset
  visibility yet") and consumed only by the Saferoom launcher's **"Open
  App"** CTA (`fortmesa.openApp`, `src/extension/saferoom-launcher.ts`) and
  the "Settings" webview. `sandbox`'s value is a per-developer
  pod URL (`*.mesa.red`, Cloudflare-WARP-gated); `next`/`latest`/`prod` are
  shared, real URLs. Non-prod entries are grouped as a clearly-marked,
  trivially-strippable block for an eventual prod-only "public vsix" — not
  built this round, see `TODOS.md`. Prod scope-branding
  (`BrandAsset.brandURLDomain`, child-scope-under-parent → a domain like
  `vciso.app`) is parked entirely — no brandAsset access this round.

## Source of truth for this file

Re-derive this table from these three files, in this order, whenever any of
them changes:

1. `src/registry/config.ts` — the zod `configSchema` (ground truth for which
   keys exist and their types).
2. `src/registry/environments.ts` — ground truth for the four environments'
   hardcoded `gateway`/`app` values (W2).
3. `package.json`'s `contributes.configuration.properties` — ground truth for
   which `fortmesa.*` settings actually exist and how VS Code presents them.
